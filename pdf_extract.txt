一 接手后的总判断
如果我以硅谷科技公司的创始人兼 CTO 身份接手这两个文档，我不会把任务交给一个“万能 Agent”去自
由发挥，也不会让十几个智能体同时改同一套代码。我要先把工作变成一个有依赖关系的交付图，再把每个
节点封装成可验收的工作包。每个工作包只允许一个主执行者修改其拥有的目录，另有独立复核者和对抗测
试者；最终由集成 Agent 或技术负责人合并。
整个项目分成三类工作。第一类是可以并行的读取、规划、数据抽取、测试生成和离线评测；第二类是需要
接口冻结后并行的连接器、索引、前端和模型适配；第三类是必须串行的规范冻结、主分支集成、权限策
略、真实写操作和发布。效率来自并行化确定性工作，而不是让多个模型同时对同一个未定义问题给出互相
覆盖的答案。

八 技术编排与状态管理
单次用户任务采用 LangGraph 风格的有状态图：模型节点负责意图解析、候选计划、证据解释和必要的追
问；确定性节点负责字段校验、过滤、成本、权限和审计。LangGraph 的 checkpointer 可以保存线程级状
态，store 保存跨线程的偏好和长期知识，适合任务暂停、人工修改、重放和恢复；相关官方文档列在参考

十一 什么时候砍功能
高效率不是尽可能多地上线功能，而是尽快确认真正有价值的闭环。以下功能在第一阶段主动砍掉：
 不做多平台全覆盖。先做一个官方/授权来源，验证检索、比较、证据和观察是否成立。
 不做游戏账号自动购买、自动登录、账号托管、账号转移或凭据接收。账号类只做公开挂牌和风险核
验。
 不做自由浏览器 Agent。先做 API 和只读浏览器，再做审批和有限写操作。
 不做自研基础大模型。先用 Model API 和本地模型适配层，把工程优势建立在连接器、证据和安全上。
 不做没有评价集的“智能排序”。先建立真实用户查询、硬约束和反馈回归集。
 不做不可解释的个性化。用户看到每条推荐的来源、数据时点、约束匹配和风险。

十三 最终验收清单
 用户输入一句自然语言或上传图片后，系统能生成可读的 SearchSpec，并指出缺失条件。
 至少一个合规来源能够完成采集、规范化、去重、过滤、排序、证据卡和原平台跳转。
 预算、地区、库存和必选规格等硬约束违反率为 0；未知字段不会被模型补写。
 每个关键字段都能查看来源 URL、抓取时间、证据片段和冲突状态。
 单次任务可以暂停、人工修改、恢复和重放；重复执行不会产生重复副作用。
